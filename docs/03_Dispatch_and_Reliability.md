# 03 — Dispatch and reliability contract

> **After [ADR-0011](adr/0011-staff-app-and-three-roles.md):** an offer's response window starts when the valet's app acknowledges it is on screen with an explicit command (previously: when WhatsApp accepted the message; a read never starts it — [ADR-0012](adr/0012-admin-access-and-offer-acknowledgement.md)); the hard limit from reservation is unchanged. Relayed actions require the valet's device to be marked as not working, not a WhatsApp outage.

These are proposed engineering rules implementing the approved automatic-assignment process. They must be tested against a real transactional database.

## Queue and candidate selection
1. Persist every authorized guest request once. Retain original request time even if it arrives while parking is in progress.
2. A request becomes dispatch-eligible when the vehicle is PARKED, contact/fallback is usable, no movement-blocking hold exists and the event has an active operating team.
3. Select the oldest eligible unassigned request within the event. An ineligible early request does not block every other vehicle. Once eligible, it keeps its original age.
4. Prefer that ticket's `parked_by` only if enabled, on this event's active shift, available and without a live reservation/task.
5. Otherwise use the longest-idle eligible valet, with a stable staff-ID tie-break. Do not wait for the original valet while another is free.
6. A free valet cannot bypass an older eligible request simply because they parked a newer request's vehicle.
7. Reserve request and candidate in one database transaction. Commit a targeted message to the outbox in the same transaction. Then deliver the message asynchronously.
8. Recheck all rules when the valet accepts. Staff are instructed not to move the vehicle until acceptance is confirmed by the system.

## Proposed initial settings — tune during the pilot
| Setting | Initial target/default | Meaning |
|---|---|---|
| Offer response window | 30 seconds | Begins when the send is accepted by the provider, subject to hard reservation limit |
| Reservation hard limit | 60 seconds from reservation | Prevents notification failures from trapping staff capacity |
| Send pending warning | 15 seconds | Surface slow offer delivery to worker monitoring |
| Attempts before supervisor alert | 2 failed offers | Alert; continue safe dispatch attempts if eligible candidates exist |
| Candidate timeout cooldown | 60 seconds per request | Avoid repeatedly selecting the same silent valet |
| Guest wait warning | 4 minutes from original request | Proposed baseline preserved from old guide |
| Guest wait critical | 6 minutes | Escalate with current stage and owner |
| Accepted retrieval warning | 4 minutes after acceptance | Alert only; no automatic custody reassignment |
| Ready awaiting guest warning | 5 minutes | Keep assigned valet busy; supervisor can manage exception |

The earlier guide described a 90-second acceptance default. This pack proposes 30 seconds to support faster reassignment. These are configurable pilot choices, not measured venue SLAs. Configuration changes are audited. An issued offer keeps its original deadline; do not silently rewrite active offers when settings change.

## Atomicity and stale actions
Use a single per-event dispatcher leader/transaction lock for predictable queue order at V1 scale, plus database uniqueness constraints as the final guard. Workers may wake concurrently, but only one can commit the same reservation. A partial unique index can enforce a single live task on each staff/vehicle resource. Choose and document a consistent lock order.

Every offer has a monotonic generation/version and opaque action ID. Acceptance checks task ID, generation, candidate, event, expiry and state in one transaction. If timeout and acceptance race, exactly one transition wins. The loser returns a truthful “no longer available” response. A late callback cannot reactivate expired work.

For unaccepted offers: decline, send failure or expiry releases reservation, records the failed attempt and requeues. For accepted work: loss of contact or elapsed time alerts a supervisor. Transfer requires establishing where the key/car are, cancelling old action authority and the new valet acknowledging custody. Never transfer based only on “last online”.

## Durable messaging and background work
- Store inbound webhook receipt before asynchronous processing; return the provider acknowledgement only after durable receipt. Validate origin/signature first using the provider's current official scheme.
- Deduplicate inbound message IDs; for status events use a composite event identity/status transition rather than discarding all statuses for the same message ID.
- Keep a transactional outbox for notifications generated by committed business changes. A crash between commit and send cannot lose the notification.
- Workers use bounded exponential backoff, retry classifications and a dead-letter state with an operator-visible resolution path.
- Rebuild due work from stored deadlines and statuses after a restart. A periodic reconciliation scan repairs missed wakeups. Queue/broker loss must not erase ticket state.
- An outbound request can time out after the provider accepted it. Mark DELIVERY_UNKNOWN, reconcile where possible and avoid blind immediate resends. External message duplication is still possible; all embedded operations remain idempotent.
- Track delivery/read/failure as events. Do not let an older callback regress READ/DELIVERED to SENT; retain failure history and surface contradictions for investigation.
- Never execute an external network call while holding long-lived database locks.

## Failure behavior
| Failure | Expected behavior |
|---|---|
| Guest taps repeatedly | Return the existing request/status; no extra job |
| Two valets accept stale/duplicate offers | Only the current reserved candidate and generation may win |
| Worker crashes | Persisted inbox/outbox/deadlines allow safe recovery |
| WhatsApp unavailable | Keep state, show outage, queue allowed messages; supervisor-assisted operations with explicit identity verification |
| Phone invalid / wrong recipient | Stop further messages; revoke prior credentials; correct and re-confirm in person |
| Guest without working phone | Supervisor verifies and records assisted service; no fabricated contact data |
| No staff available | Queue visibly; age continues; alert on configured thresholds |
| Accepted valet goes offline | Alert and resolve custody before transfer |
| Database unavailable | Do not acknowledge new writes as successful or continue automatic dispatch |
| Web console loses connection | Stale-data banner; disable unsafe mutations; refresh server state before retry |
| Media upload fails | Retry visibly; keep incomplete photo status or authorized exception |
| Event ends with car present | Carryover custody process, not fake delivery |

No untested offline mode is promised. During a total service outage, staff use an agreed human continuity procedure, preserve custody, and reconcile records afterward. Replacing that with a synchronized offline app would be a separate product decision.

## Telemetry
Emit correlation IDs across webhook → command → ticket transition → outbox. Monitor queue age, worker heartbeat, inbox lag, failed messages, expired offers, DB errors and unresolved holds. Logs must mask phone numbers, collection codes and tokens. Store detailed incident evidence in access-controlled records, not public logs.
