# Inputs required before a staging deployment

See also: [staging/hosting-options.md](staging/hosting-options.md) (comparison and recommendation),
[staging/whatsapp-onboarding.md](staging/whatsapp-onboarding.md) (checklist),
[../infra/staging/oci-riyadh-plan.md](../infra/staging/oci-riyadh-plan.md) (draft, not applied).

Nothing here is a secret value. Values are set in the hosting provider's secret store, never in chat or
in this repository. Staging is **not deployed** from this branch; this list is what the owner supplies.

## Hosting and network

| Input | Used for | Notes |
|---|---|---|
| Hosting provider + region (KSA data residency preference) | ADR-0005 | Managed PostgreSQL 16+ (tested on 18.7), one web + one worker process |
| Staging hostname (e.g. `staging.<domain>`) | `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS` | HTTPS only; console and webhook on the same host |
| Reverse-proxy topology | `TRUSTED_PROXY_COUNT` | Exact count of proxies appending `X-Forwarded-For`; wrong value breaks login throttling |
| Private S3-compatible bucket (no public access, encryption at rest, versioning) | `MEDIA_STORAGE=s3`, `MEDIA_S3_BUCKET`, `MEDIA_S3_REGION`, `MEDIA_S3_ENDPOINT_URL` (non-AWS) | Credentials via workload identity or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` in the secret store |
| Container platform able to run the image's three process types | infra/staging/README.md | Web, always-on worker, one-off release job |
| Backup + restore target | Runbook "database restore" | Restore must be rehearsed once before Gate 4 |

## Secrets (generated by the owner, stored in the secret store)

| Name | Format |
|---|---|
| `DJANGO_SECRET_KEY` | ≥ 50 random characters |
| `FIELD_ENCRYPTION_KEY` | Fernet key (urlsafe base64, 32 bytes) |
| `HASH_KEY` | ≥ 32 random bytes |
| `DATABASE_URL` | `postgres://…` for the managed instance |

## WhatsApp Cloud API (none verified yet; all current WhatsApp results are SIMULATED)

| Input | Name / where |
|---|---|
| Meta Business portfolio verified, WhatsApp Business Account | Owner action in Meta Business Manager |
| Dedicated business phone number registered to Cloud API | `WHATSAPP_PHONE_NUMBER_ID` |
| System-user access token with `whatsapp_business_messaging` | `WHATSAPP_ACCESS_TOKEN` |
| App secret (webhook signature) | `WHATSAPP_APP_SECRET` (+ `WHATSAPP_APP_SECRET_PREVIOUS` during rotation) |
| Webhook verify token (owner-chosen random string) | `WHATSAPP_VERIFY_TOKEN` |
| Approved utility templates (AR + EN) for messages sent outside the 24-hour window | Names listed in `docs/04` |
| Webhook URL registered in the Meta app | `https://<staging-host>/webhooks/whatsapp` |
| Test phone numbers for valets and guests (synthetic people, real handsets) | Gate 4 rehearsal |

## Accounts (created on the server, never through chat)

| Step | Command |
|---|---|
| First super admin | `uv run python manage.py createsuperuser` then link a `Staff` row (runbook "bootstrap") |
| MFA enrolment for manager+ | `uv run python manage.py issue_mfa <username>` — the URI is shown once on the server console |

## Environment flags for staging

`SALLIMHA_ENV=staging` (required; the app refuses to start without it), `DJANGO_DEBUG=0`, `SIMULATOR_ENABLED=0`,
`WHATSAPP_TRANSPORT=cloud`, `SECURE_HSTS_SECONDS=3600`. Release gate: `python manage.py deploy_check`.
Settings refuse to start if the simulator or the fake transport is enabled outside local/test.
