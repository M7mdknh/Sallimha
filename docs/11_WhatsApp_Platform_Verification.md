# 11 — WhatsApp platform verification (Phase 0 spike)

Checked 15 Nov 2026 against official Meta/WhatsApp documentation. **Documentation evidence only — no real WhatsApp account was used.** Every item marked “staging” must be re-verified with the real test sender before Gate 4.

| # | Question | Finding | Source | Design consequence | Staging check |
|---|---|---|---|---|---|
| 1 | How are webhooks authenticated? | Meta signs requests with HMAC-SHA256 of the payload using the app secret, sent as `X-Hub-Signature-256: sha256=<hex>`. During app-secret rotation, accept either secret for a transition period | developers.facebook.com WhatsApp Cloud API webhook docs (Get Started / webhooks) | Verify over the **raw body** before parsing or persisting; constant-time compare; support two secrets (`WHATSAPP_APP_SECRET`, `WHATSAPP_APP_SECRET_PREVIOUS`) | Yes |
| 2 | Can template quick-reply buttons carry a per-send payload? | Yes: send-time `components: [{type: "button", sub_type: "quick_reply", index, parameters: [{type: "payload", payload}]}]`; tap arrives as `messages[].type = "button"` with `button.payload` and `button.text`, plus `context.id` of the original message | Template components docs; Button messages webhook reference | Opaque action references ride in the payload; `context.id` is recorded as secondary evidence | Yes |
| 3 | Interactive reply buttons | Up to **3** reply buttons; title ≤ **20** chars; id ≤ **256** chars; tap arrives as `interactive.button_reply {id, title}` | Interactive reply buttons messages docs | Valet/guest prompts limited to 3 buttons; Arabic labels checked for length | Yes |
| 4 | Customer-service window | Opens and resets with **each user message**; free-form replies allowed within 24 h; outside it only approved templates | WhatsApp Business Messaging Policy | Transport chooses template vs session by stored last-inbound time per recipient | Yes |
| 5 | Does a button tap open the window? | Not stated explicitly. A tap is delivered as an inbound user message, so it is expected to count | Inference from #2/#4 | READY (with code) is sent as a session message when the window is open, template otherwise | **Must verify** |
| 6 | Opt-in | Business may contact a user only if they gave their number/username **and** opted in to receive messages | Messaging Policy | Intake records service-messaging permission at phone confirmation; no marketing use | — |
| 7 | Sender identity | Inbound messages always include `from_user_id` (business-scoped user ID, “BSUID”); `from` (phone) and `contacts[].wa_id` may be **absent** for users who adopted a username. Meta: “Build your integration to identify users by BSUID.” | Messages webhook reference | Guest binding stores phone (encrypted + keyed hash) and the BSUID once learned. First inbound with matching phone binds the BSUID; if phone is absent, binding accepts the BSUID only when a valid action reference **and** `context.id` point to a message sent to this binding, and records that basis | Yes |
| 8 | Status webhooks | `statuses[]` with `id`, `status` (sent/delivered/read/failed), `timestamp`, `recipient_id`, optional `recipient_user_id`, `errors`, `conversation`, `pricing`; up to three status webhooks per outgoing message | Messages webhook reference | Status events keyed by (message id, status, timestamp); monotonic status rank prevents regression (AT-27) | Yes |
| 9 | Template category for a message containing a code | Utility templates are for user-triggered transactional updates; marketing content is re-categorised. The docs fetched did **not** state whether a handover code forces the authentication category | Utility templates docs | Prefer session message (#5). Category decided at template submission | **Must verify** |
| 10 | Pricing/latency of valet offer templates | Not determined from documentation | — | Measure in staging; offer timer starts when provider accepts the send (docs/03) | **Must verify** |

## Fake transport used in Phases 0–2
The local fake transport produces and accepts payloads in the shapes above, signs simulated webhooks with a local test secret, and stores simulated phone inboxes for the demo simulator. All results produced with it are labelled **SIMULATED** and are not evidence of real integration.
