# Sallimha Phases 0–2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
> Execution chosen by the user: implement in this session without per-step approval (native, superpowers:executing-plans).

**Goal:** A locally runnable, tested Sallimha: WhatsApp-first valet flow (simulated transport), deterministic atomic dispatch on PostgreSQL, durable worker, and an Arabic-first role-based console — Gates 2 and 3 of docs/06.

**Architecture:** Django 6.1 modular monolith (`services/api`) with apps `core` (crypto, phone, audit, idempotency, locks, logging), `ops` (organization, staff, events, shifts, tickets, tasks, requests, custody, incidents, reports, config — models and services split by module), `messaging` (inbox/outbox, transport adapter, fake transport + simulator, valet and guest conversation flows) and `console` (DRF API). One worker process (`manage.py run_worker`) drives inbox, outbox, deadlines and dispatch from PostgreSQL rows. React + TypeScript + Vite console in `apps/web`, served same-origin via proxy.

**Tech Stack:** Python 3.14, Django 6.1.3, DRF 3.18.3, psycopg 3, PostgreSQL 18 (Docker Compose), phonenumbers, cryptography (Fernet), pyotp, pytest + pytest-django, ruff; Node 24, React 19, TypeScript, Vite, @playwright/test.

**Spec:** `CLAUDE.md`, `docs/01`–`07`, `docs/11`, `DESIGN.md`, `docs/adr/0001`–`0006`, `docs/09_Traceability_Matrix.md`.

## Global Constraints
- PostgreSQL is the source of truth; no in-memory-only locks or timers; constraints per ADR-0003 (#1–#13).
- One open retrieval request per ticket; ≤1 live task (RESERVED/OFFERED/ACCEPTED) per valet; ≤1 live movement task per ticket; ≤1 open shift per person; ≤1 unreleased key per `(key_station, hook)`.
- Default timings (docs/03): offer window 30 s from provider-accepted send; hard reservation 60 s; send-pending warning 15 s; alert after 2 failed offers; cooldown 60 s per request; guest wait warning 240 s / critical 360 s; accepted warning 240 s; ready warning 300 s. Issued offers keep their deadline.
- Collection code: 6 random digits, HMAC verifier, created at READY, 5 failed attempts → supervisor review, consumed at delivery, revoked on phone correction/cancel.
- Opaque action references: `secrets.token_urlsafe(24)`, stored only as keyed hash, bound to ticket + binding revision (guest) or staff + task + generation (valet), single-use, expiring.
- WhatsApp: interactive reply ≤3 buttons, titles ≤20 chars, ids ≤256 chars; webhook `X-Hub-Signature-256: sha256=<hex HMAC-SHA256(raw body, app secret)>`, two secrets accepted; identity by `from_user_id` (BSUID) or phone.
- Arabic default, English supported; identifiers in isolated LTR spans; Asia/Riyadh display, UTC storage; digits 0–9 for identifiers.
- Logs never contain phone numbers, codes or tokens (masking filter).
- Simulated transport results are labelled **SIMULATED**; real provider = BLOCKED.
- Supervisors: monitoring, shift operations, exceptions — **no** manual routine-dispatch endpoint.
- Brand: `brand/tokens.css` v1.0.1 tokens, self-hosted Noto fonts, supplied SVGs only.

## Review Focus
1. Arabic-Indic / Persian digits and stray spaces/dashes in phone, hook and code input → normalized, never mis-parsed across fields. Pinned in Task 1.0 (`test_normalize_digits_*`) and Task 1.4 (`test_numeric_text_outside_prompt_is_not_guessed`).
2. A guest whose inbound webhook lacks a phone (`from` absent, `from_user_id` only) → still served if the action reference and `context.id` match; otherwise identity exception. Pinned in Task 1.5 (`test_bsuid_only_sender_binds_via_context`).
3. Worker killed between claiming an outbox row and recording the result → lease expiry, `DELIVERY_UNKNOWN` (not resent blindly). Pinned in Task 1.10 (`test_lost_response_marks_delivery_unknown`).
4. Two console tabs / double click on an exception action → one effect (Idempotency-Key). Pinned in Task 1.8 (`test_repeat_submit_same_key_single_effect`).
5. Valet goes on break or shift end requested while holding an accepted retrieval → break pending, shift end refused, no silent release. Pinned in Task 1.6 (`test_break_pending_until_handover`).
